# 機器側の構成

送信機（TX）と受信機（RX）は同じプログラムを役割違いで動かします。GStreamer と iperf はコマンドとして起動せず、自作の常駐プログラムにライブラリとして組み込みます。パイプラインはコードの中で組み立て、画面とのやり取りは `/api/v1` だけにします。

> **試作の段階の進め方（2026-11-04 の決定）**
> いまは試作の段階なので、制御プロセス（Rust の常駐プログラム）が、いまある映像のプログラム（送信・エンコード制御・受信・再生。一部は Python）を **子プロセスとして起動して動かします**。設定はそれぞれの起動引数と環境変数で渡し、統計はそれぞれが書き出すファイルと出力から読みます。
> そのため、この文書の次の決まりは **製品化の段階に先送り** します。
> - 設定を起動引数や環境変数で渡さない（Unix ソケットで渡す）
> - 機器に Python を置かない
> - パイプラインをプロセスの中で組み立てる、回線テストをライブラリとして組み込む
> - 「2. 外から見えるもの（隠し方）」の対策すべて（プロセス名・スレッド名・ディスク上のファイル名・パッケージ名など）
>
> プレビューも同じ扱いで、制御プロセスが最初の視聴の申し込みでプレビュー用のプログラム（Python）を子プロセスとして起動し、標準入出力でやり取りする。映像は送信・再生のプログラムから Unix ソケットで写し取る。
>
> 先送りしないもの：画面・API（パス、項目名、コード）・利用者に見えるログの文・HTTP ヘッダには実装の名前を出さない（`npm run check:terms`）。オフラインで動く。GPL のエンコーダを使わない。API の値と子プロセスの統計の対応は「5. API との対応」を参照。

```
PC・タブレットのブラウザ
   │  HTTP + WebSocket（/api/v1。中立な名前だけ）
   ▼
┌──────────── 送信機 TX-01 ─────────────────────────────┐
│ 制御プロセス   画面の配信・API・設定・状態・ログ          │
│      │ Unix ソケット（設定と統計をやり取り）              │
│ 映像プロセス   GStreamer・libiperf をライブラリとして内蔵  │
└──────┬──────────────────────────────────────────────┘
       │  LAN（映像は UDP）
       ▼
   受信機 RX-02（同じ構成で受信側）
```

## 1. プロセス

### 制御プロセス（例：`/opt/<製品名>/bin/<製品名>d`）

- `web/dist` をバイナリに埋め込んで配信する（ディスクに HTML を置かない）。
- `api/openapi.yaml` の REST と `/api/v1/live` の WebSocket を実装する。
- 設定の保存と適用（`version` による楽観ロック）、状態の管理（`LinkState`）、イベントとログ。
- API の項目名・エラーコードは `docs/terms.md` の言葉にそろえる。ブラウザの開発者ツールで見えるのは API なので、ここに実装の名前を出さない。
- HTTP ヘッダ（`Server` など）にもフレームワーク名を出さない。

### 映像プロセス（例：`/opt/<製品名>/libexec/<製品名>-engine`）

- GStreamer の API で要素を一つずつ作ってつなぐ。`gst-launch` も、パイプライン文字列を渡す `gst_parse_launch` も使わない。
- 要素には必ず中立な名前を付ける（`in0`、`enc0`、`mux0`、`out0` など）。GStreamer は処理スレッドに「要素名:パッド名」を付けるため、既定名のままだと `srtsrc0:src` のように見える。
- 設定は起動引数や環境変数で渡さず、Unix ソケットで制御プロセスから受け取る（引数と環境変数は /proc から読める）。
- 統計（RTT、損失、再送、推定帯域、映像遅延など）を読み、API の中立な名前に直して制御プロセスへ返す（対応は `docs/terms.md`）。
- プレビュー：伝送する AV1 をそのまま二分岐して写し取る（送信機は送り出す直前、受信機は表示に合わせて）。写し取りは待たない作りで、読み手がいないときは何も写さないので、伝送と受信機の表示を邪魔しない。プレビュー用の処理がそれを復号し、H.265（ブラウザが対応していなければ H.264）でビットレートを多めにして圧縮し直し、webrtcbin（WebRTC）でブラウザへ送る。STUN・TURN は使わず LAN の中だけ。ブラウザとの手順は `POST /api/v1/preview/sessions`（offer → answer）と `DELETE`（`docs/api.md`「プレビュー」）。見ている画面がなくなって 30 秒たつと止まる。ハードウェアの復号・圧縮（VA）を使うので CPU はほとんど使わない（4K で、見る人ひとりにつき 1 コアの約 6〜9 %）。
- 回線テストは libiperf（iperf3 のライブラリ版）をリンクして行う。iperf3 コマンドは起動しない。受信機側のサーバーはテストの間だけ、既定の 5201 番以外のポートで動かす。
- 二つに分ける理由：エンコーダやドライバの不具合で映像側が落ちても、画面は「再接続中」を出したまま映像プロセスを立て直せる。

### 言語

- Rust を推奨（gstreamer-rs は GStreamer の開発者が保守しているバインディング。Web は axum、静的ファイルの埋め込みは rust-embed。単一バイナリで配れる）。C++ でもよい。
- Python はソースがそのまま機器に置かれるので使わない（試作の段階では、いまある Python のプログラムを子プロセスとして使う。上の注記を参照）。

## 2. 外から見えるもの（隠し方）

| 見える場所 | 対策 |
| --- | --- |
| `ps` / `/proc/<pid>/cmdline` | パイプラインをプロセス内で組むので、見えるのは製品名のバイナリだけ |
| スレッド名（`top -H`、`ps -T`） | 要素に中立な名前を付ける。libsrt は自分のスレッドを `SRT:RcvQ:w1`、`SRT:SndQ:w1`、`SRT:TsbPd`、`SRT:GC` と名付けるので、名前の部分を変更するか（MPL 2.0：変更したファイルのソース公開が必要）、下の /proc の設定で他ユーザーから見えなくする |
| `/proc/<pid>/environ`・`maps`・`fd` | 専用のサービスユーザーで動かす（他ユーザーは読めない） |
| プロセスの一覧そのもの | `/proc` を `hidepid=invisible`（古いカーネルは `hidepid=2`）でマウントする |
| ディスク | GStreamer は OS のパッケージに頼らず、必要なプラグインだけビルドして `/opt/<製品名>/lib` に同梱する（gstreamer-full で 1 つのライブラリにまとめられる）。`gst-launch-1.0`・`gst-inspect-1.0` は入れない。プラグイン一覧のキャッシュ（registry）も非公開の場所に置く |
| 設定とログ | 設定は 0600、ログディレクトリは 0700。画面と journal には中立な文とコードだけ。GStreamer のエラー文には要素名が入るので、そのまま出さない |
| 環境変数 | 起動時に `GST_` で始まる変数を消す。リリース版はデバッグ出力なしでビルドする |
| バイナリの中の文字列 | 要素名は文字列として残る（`strings` で読める）。文字列の難読化で手間を増やすところまでは可能 |

### 隠し切れないもの

- root 権限があり解析する気のある人からは隠せない。目標は「ふつうの確認手段（ps、画面、API、ログ、設定ファイル）では分からない」。
- 暗号化されるのは映像の中身だけで、接続手順のパケットは暗号化されない。LAN でパケットを取って調べれば分かる。そこまで隠すなら送受信機の間を WireGuard で包む（設定の手間と負荷が増える）。

## 3. オフラインで動かす

- 画面のフォント（Geist）は同梱済み（`@fontsource-variable/geist`）。日本語は端末側のフォントで表示する。
- インストーラは依存ライブラリを全部含めた .deb（またはアーカイブとインストールスクリプト）にして USB から入れる。systemd のサービスとして自動起動。
- 機器をこちらで用意するなら、OS イメージごと出荷するのが一番確実。
- プレビュー（WebRTC）も外部のサーバーなしで動く（STUN・TURN を使わず、LAN の中の候補だけでつなぐ）。

## 4. ライセンス（出荷前に専門家に確認すること）

- **GStreamer（LGPL）**：動的リンクのまま同梱すれば、自作部分を公開する必要はない。ライセンス表示と、利用者がライブラリを差し替えられることが条件。LGPL は「改変と、そのデバッグのためのリバースエンジニアリング」を認めるよう求めているので、利用規約でリバースエンジニアリングを全面的に禁じない。
- **映像のエンコーダ**：映像は AV1 のソフトウェアエンコーダで作る。GPL のエンコーダ（x264 など）はプログラム全体の公開を求められるおそれがあるので使わない。AV1 のエンコーダのライセンスと特許の条件は出荷前に確認する。
- **プレビューの圧縮**：H.265 / H.264 はハードウェアの圧縮（VA）を使い、GPL のエンコーダ（x264・x265）は使わない。H.265 / H.264 の特許の条件も出荷前に確認する。
- **libsrt（MPL 2.0）・iperf3（BSD）**：ライセンス表示が必要。libsrt のファイルを変更したら、そのソースの公開も必要。
- ライセンス一覧には名前が出るので、運用画面ではなく「機器情報」のライセンス表示や添付文書に置く。

## 5. API との対応（実装メモ）

試作の段階では、下の値を子プロセスの統計（送信側の高速統計、エンコード制御の記録、受信側の統計、再生側の 1 秒ごとの出力）から 1 秒ごとの差分で作る。

| API | 取り方 |
| --- | --- |
| `Stats.rtt_ms` | 送受信の統計の RTT（`msRTT`） |
| `Stats.loss_pct` | 送信機：再送パケット数 ÷ 送信パケット数（`pktRetrans` / `pktSent`。NAK による損失数は RTT が大きいと多めに出るので使わない）。受信機：損失パケット数 ÷ 届くはずのパケット数 |
| `Stats.loss_threshold_pct` | 標準の遅延では `null`（損失は再送で補うので警告しない） |
| `Stats.retrans_pct` | 受信機だけ。再送で届いたパケットの割合。送信機は `null` |
| `Stats.send_mbps` | 送信バイト数の差分（再送分を含む） |
| `Stats.target_mbps` / `actual_mbps` | エンコード制御のいまの目標 / エンコーダの出力の実測（5 秒平均） |
| `Stats.bandwidth_mbps` | 送信待ちが溜まっているときの ACK レートからの推定（`nd_c`）。溜まっていないときは `null`（`mbpsBandwidth` は使わない） |
| `Stats.delay_margin_s` / `delay_margin_warn_s` | never-drop 制御の残り予算（D0 − H。小数 1 桁は切り捨てで、`delay_margin_low` の `margin_s` と同じ値にする）。警告の基準（標準の遅延では 3 秒）を `delay_margin_warn_s` で返し、下回ったら `delay_margin_low` |
| `Stats.send_late_5m` | 送信側で破棄したパケット（`pktSndDrop`）の直近 5 分（never-drop ではふつう 0） |
| `Stats.unrecovered_5m` | 受信側で回復できなかったパケット（`pktRcvDrop` ＋ 欠番）の直近 5 分 |
| `Stats.stalls_5m` / `stall_s_5m` | 再生側が数えた映像の停止の回数と合計秒数（直近 5 分） |
| `Stats.delay_profile` / `delay_target_ms` / `TransportSettings.delay` | 遅延のプロファイル（daemon の `src/profile.rs`）。標準：送受信の `latency`（`SRTO_LATENCY`）8000 ms と再生まで 9.5 s。低遅延：約 1.5 s（標準に preset 10・先読みなし、小さなメッセージをすぐ送る、固定のビットレート、表示の待ち 400 ms と余裕の見張りを足したもの。device.toml の `[profile_low]`）。送信機は伝送を始めるときに伝送設定の遅延を使い、接続のときにストリーム ID（`SRTO_STREAMID`、`delay=low` など）で受信機に伝える。受信機は、受信プログラムが出すストリーム ID の行を見て、再生プログラムの制御の入力（`--ctl-fd`）に低遅延の行を書き、計測値をそのプロファイルに切り替える（`follows_peer: true`）。受信機の `delay_target_ms` は、再生プログラムが自分で足した待ち時間（`ts_offset_ms` の増え分）を含む |
| `VideoOptions.auto_available` / 影響 `low_delay_fixed` | 低遅延のあいだは、保存した `encode.mode` によらず固定のビットレート（`encode.manual`）で送る（おまかせは効かない）。映像設定は書き換えない |
| `Stats.video_latency_ms` | 受信機の実測（送信機に入った時刻と表示時刻の差）。測れるまでは `null` |
| `OutputSettings.display` / `POST /display` / `Stats.display` | 受信機のモニター。試作の段階では、再生プログラムの制御の入力（`--ctl-fd`）に `display <mode>` を書き、再生プログラムが自分のウィンドウ（`waylandsink`）で映す。1 秒ごとの出力の `display` を `on` / `off` / `failed` にし、映せないあいだは 30 秒ごとに書き直す。デスクトップの表示の変数（`WAYLAND_DISPLAY` など）は再生プログラムにだけ渡す |
| `Media.label` | 画面に出す名前。カメラは名前（例「Facecam 4K」）、ファイルはフォルダーを除いたファイル名。デバイスのパスは出さない |
| `Impact reconnect_gap` / `input_switch_gap` の `gap_s` | 接続をやり直したときに受信側の映像が途切れる秒数。遅延の設定でおよそ決まる（標準で約 10 秒） |
| `Event bitrate_changed` | エンコード制御の判断と切り替え完了の記録から。理由は損失 → `loss`、送り出しの遅れ → `delay`、上げ → `recovered`、操作 → `manual` |
| `Alert peer_rejected_passphrase` | 接続拒否の理由がパスフレーズ不一致のとき（`SRT_REJ_BADSECRET`）。暗号化ができてから |
| `POST /preview/sessions` | 試作の段階ではプレビュー用の子プロセスに offer を渡し、answer を返す。プレビューが無効・起動できない・時間切れは `503 preview_unavailable`、`live` 以外は `409 not_live`、上限（既定 3 画面）を超えたら `429 too_many_viewers` |
| `TransportMode outbound / inbound / mutual` | caller / listener / rendezvous（いまは送信機が caller、受信機が listener だけ） |
